# GUR-163: How the cv agent could pull pipeline images and run a multi-container ROS 2 simulation

Research note, 2026-10-16. It lists options, costs, and unknowns. It does not choose a design.

Question: what would the Jenkins `cv` agent need to pull images from the pipeline registry (`registry:5000`) and run a multi-container ROS 2 simulation (Gazebo plus several composed service containers) on today's stack? The note covers four sub-questions. For each one, it gives the current state and then the options:

1. How the agent reaches a container engine today, and what the image-build agent and builder already do that could be reused.
2. How the cv agent could reach the registry without publishing the registry outside the stack.
3. How ROS 2 DDS discovery works between sibling containers, and what limits it in this stack.
4. Whether `sdi-integration dispatch-local` can run the same path on a developer host.

The research did not start the Jenkins stack. Every repository claim cites a file at `origin/main` `e9a54f6`.

## 1. The current stack

### The cv agent has no container engine

- **Container settings.** `cv` builds from the plain `agent` target of `deployment/jenkins/agents/Dockerfile`. It runs with `read_only: true`, `cap_drop: [ALL]`, and `no-new-privileges:true`. It has tmpfs mounts on `/home/jenkins/agent` and `/tmp`, and it joins only `networks: [controller-cv]` (`deployment/jenkins/compose.yaml`, service `cv`). Its base image is `JENKINS_CV_AGENT_IMAGE`, which `bin/stack` reads from `cv-fixture-v1.yaml` (`deployment/jenkins/bin/stack:688`). That base is the same pinned `python@sha256:229a…` image the other agents use.
- **Network.** `controller-cv` is internal only when `JENKINS_AGENT_NETWORK_INTERNAL` is true. The default is `false`, so the agent has general egress for the GitHub checkout (`compose.yaml` `networks:`).
- **The smoke check asserts that no agent has an engine or the builder.** On every agent, `deployment/jenkins/bin/smoke-check` runs `test ! -e /var/run/docker.sock` (line 489). On every agent except `image-build`, it fails when `buildctl` exists or when `buildkitd` or `registry` resolves (lines 501–510). It also fails when any peer agent resolves. `deployment/jenkins/README.md` lists "missing Docker access, and runtime network isolation" among the proven properties.
- **The CV adapter is a Fixture today.** The CV adapter is `sdi-fixture-adapter` (`deployment/jenkins/adapters/cv-fixture-v1.yaml`). Its work limit is 2700 s (`integration/stage-profiles/cv-v1.yaml`, `config/controller.env.example`).
- **The CV inputs already include the image-build result.** `cv-v1.yaml` takes the slots `requirements_specification`, `target_profile`, `composition_blueprint`, `deployment_schema`, and `image_build_result`. It outputs `validation_evidence`.

### Parts of the image-build path that could be reused

- **The client/daemon split.** The image-build agent stays read-only, has no capabilities, and holds only the `buildctl` client. The privileged work runs in a separate pinned service, `buildkitd`, with `privileged: true`. The client reaches the daemon over plain TCP (`tcp://buildkitd:1234`) on the internal network `image-build-builder`. The deployment README says that "network membership is the access boundary" (`deployment/jenkins/README.md` "Builder And Pipeline Registry"; `buildkit/buildkitd.toml`).
- **Constant addresses and a fixed environment.** The adapter's environment holds only `PATH` and `LC_ALL`. For that reason, `BUILDKIT_ADDRESS` and `REGISTRY = "registry:5000"` are module constants. `buildctl` gets an empty `HOME` and `DOCKER_CONFIG` (`integration/src/sdi_pipeline_integration/_image_build_adapter.py:1-12, 63-64, 559-569`). The runtime builds that environment for every adapter (`_stage_runtime.py:1486-1493`).
- **Preflight checks that map to outcome codes.** The adapter checks the builder (`buildctl debug workers`) and the registry (`GET /v2/`) before it does any work. Each failure maps to a closed outcome code, `builder-unreachable` or `registry-unreachable` (`_image_build_adapter.py:215-249`).
- **A work-limit shutdown sequence.** At the work limit minus 60 s, the adapter sends SIGTERM to running clients. It sends SIGKILL 15 s later (`integration/README.md` "Image-build Adapter").
- **What image-build hands to CV.** Each `BuiltImageRecord` holds `repository` (`sdi/<service_id>`) and a digest. The digest is an index for multi-arch builds and a plain manifest for single-arch builds. The result also holds `registry: "registry:5000"` (`_domain_contracts.py:219-282`). The pushed tag is `registry:5000/sdi/<service_id>:<artifact_id>-<execution id>` (`integration/README.md`). CV can therefore pull by digest and does not need the tag.
- **Registry settings.** The registry image is `registry:3.1.2`, pinned by digest. It runs read-only with `cap_drop ALL`, serves plain HTTP, and has no published port. It joins only `image-build-builder`. Its storage is the named volume `pipeline-registry` (`compose.yaml`).
- **Smoke-check pattern.** The smoke check builds a scratch image for both architectures, pushes it, and reads the index back by digest (`bin/smoke-check:48-122`). A cv-side pull check could follow the same pattern.

## 2. Options for the container engine

| Option | What it is | Costs and risks | Primary-source notes |
| --- | --- | --- | --- |
| A. Host socket ("Docker-outside-of-Docker") | Bind-mount the host `/var/run/docker.sock` into `cv` | The cv agent would control the host daemon, which is root-equivalent. Bind mounts can expose the host filesystem. The agent workspace is a tmpfs inside the agent, so `-v <workspace>:…` paths would resolve on the host, not in the agent, and inputs would need `docker cp` or volumes. The sibling containers would run on host-daemon networks. The host daemon pulls with host DNS, so `registry:5000` would not resolve (see section 3). Breaks the smoke assertion `test ! -e /var/run/docker.sock`. Cleanup after timeouts would need labels or a Compose project per Execution ID. | Docker: "only trusted users should be allowed to control your Docker daemon". A container can mount the host root and "alter your host filesystem without any restriction". [Docker Engine security](https://docs.docker.com/engine/security/) |
| B. Docker-in-Docker sidecar (follows the `buildkitd` pattern) | A pinned `docker:dind` service, `privileged`, on a new internal network shared with `cv`. The agent gets only the `docker` CLI and `DOCKER_HOST=tcp://<sidecar>:2375\|2376` as a constant. | Adds a second privileged container next to `buildkitd`. The inner daemon needs its own storage volume or loses its image cache on restart. The plain-TCP API on an internal network has the same trust model as `buildkitd`, but Docker's API gives far more control than BuildKit's. The inner daemon resolves `registry` through Docker's embedded DNS when it shares a network with the registry. Needs `--insecure-registry registry:5000` (plain HTTP). Simulation containers are nested in the sidecar, so host networks stay untouched. | Docker Hub `docker` image: "`--privileged` is required for Docker-in-Docker to function properly", and DinD "is generally not recommended" outside special cases. It auto-generates TLS on 2376; plain TCP uses 2375. [docker image](https://hub.docker.com/_/docker). Insecure-registry flag: [dockerd reference](https://docs.docker.com/reference/cli/dockerd/) |
| C. Rootless DinD | `docker:dind-rootless` variant | The image docs call it "experimental", and it still needs `--privileged`. Host prerequisites are `newuidmap`/`newgidmap` and 65,536 subordinate IDs. It reduces daemon-root exposure, not the privileged flag. | [docker image](https://hub.docker.com/_/docker); [Rootless mode](https://docs.docker.com/engine/security/rootless/) |
| D. Docker API filter proxy | A proxy in front of option A or B that allows only selected endpoints | A third-party component, not from Docker, so it needs the usual library assessment from `AGENTS.md`. `containers/create` still accepts `Privileged`, `Binds`, and other settings, so an allowlist of endpoints does not by itself limit what the agent can create. | No primary Docker source endorses this. Treat it as unknown. |
| E. A purpose-built simulation runner service | A pinned privileged service with a narrow API, for example "start the scenario with these digests", with the cv agent as a thin client, as `buildctl` is to `buildkitd` | Custom infrastructure, which `AGENTS.md` allows only when no suitable library exists, with the rationale recorded. Gives the smallest agent-side surface. All engine concerns from option B still apply inside the service. | Repository precedent only (`buildkitd`) |

Cross-cutting costs:

- **Agent image.** The agent image changes: a `cv` build target, like the `image-build` target that adds `buildctl`, with a pinned client binary.
- **Smoke check.** The smoke check's per-agent assertions change for `cv`.
- **Pin maintenance.** Pin maintenance gains one more digest. `validate-installation` checks the `SDI_BUILDKIT_IMAGE` and `SDI_REGISTRY_IMAGE` pins against `compose.yaml` and `agents/Dockerfile` (`deployment/jenkins/README.md` "Pin Maintenance").
- **Backup and restore.** `stop`, `destroy`, and the recovery scope (which excludes builder and registry volumes today) need a decision for any new engine volume.
- **Image size.** The service images are full ROS 2 Jazzy installs on `ubuntu:noble` (`service-repository/*/Dockerfile.jazzy-debs`). Each pull is large, so engine cache persistence affects the 2700 s CV limit.

## 3. Options for reaching the registry from inside the stack

Which component pulls decides how the registry address resolves. `registry` is a Compose service name, and only Docker's embedded DNS on a shared user-defined network resolves it. Docker: "On a user-defined bridge network, containers can resolve each other by name or alias" ([bridge driver](https://docs.docker.com/engine/network/drivers/bridge/)). The host daemon of option A does not use that resolver.

| Option | Mechanism | Costs and risks |
| --- | --- | --- |
| R1. Attach `registry` to a second internal network | Add a network such as `cv-registry` (`internal: true`) with `registry` and the pulling engine (the DinD sidecar or runner) as members. Optionally add the `cv` agent if the agent pulls itself. | Lowest change. Network membership is already the access boundary here. The registry has no auth, so any member can also push and overwrite tags. Pulls by digest are not affected, but the cv side gets write access. The engine needs `insecure-registries: ["registry:5000"]` because the registry serves plain HTTP. Breaks the smoke assertion that only `image-build` resolves `registry`. Compose: "`internal`, when set to `true`, lets you create an externally isolated network" ([networks](https://docs.docker.com/reference/compose-file/networks/)). |
| R2. A second, read-only registry instance on the same volume | Run a second `registry:3.1.2` with `storage.maintenance.readonly.enabled: true`, mounting `pipeline-registry` read-only, on a cv-only network | Removes push rights from the cv side. Distribution documents read-only mode as a garbage-collection aid ("clients will not be allowed to write to the registry"), not as a serving mode. Whether two registry processes can safely share one filesystem volume while one writes is unknown. Distribution docs: [configuration](https://github.com/distribution/distribution/blob/main/docs/content/about/configuration.md) (`maintenance.readonly`). |
| R3. Publish on host loopback only | `ports: ["127.0.0.1:<port>:5000"]`, the same loopback-only pattern Jenkins uses, so a host daemon (option A) can pull `127.0.0.1:<port>/sdi/…@sha256:…` | The registry becomes reachable from host processes, not just the stack. That contradicts the README's statement that it has "no published port, so nothing outside the stack pulls from it". Docker marks 127.0.0.0/8 registries insecure automatically, "It isn't recommended to rely on this" ([dockerd reference](https://docs.docker.com/reference/cli/dockerd/)). Image references would need rewriting from `registry:5000` to the loopback address. Digests are unchanged. |
| R4. Host daemon `insecure-registries` with a host-resolvable name | Change host `daemon.json` and host DNS | The README places changes to the host OS and Docker under the host administrator's ownership, not the stack's (`deployment/jenkins/README.md` prerequisites; `docs/etri-installation-runbook.md`). Docker: insecure registries "should only be enabled for testing purposes". |
| R5. Daemonless fetch, then load | The cv agent (or runner) copies `registry:5000/sdi/x@sha256:…` to an OCI layout with a registry client, then loads it into the engine | Needs a registry-client library or tool (selected, pinned, assessed). The fetcher still needs network membership with `registry` (R1). It avoids configuring insecure registries on the engine. It costs a second copy of each large image on agent tmpfs or `/tmp`. Whether the target engine can load an OCI index directly is unknown. |

## 4. ROS 2 DDS discovery between sibling containers

### Facts from primary sources

- **Default middleware and Gazebo release.** ROS 2 Jazzy's default RMW is `rmw_fastrtps_cpp` (Fast DDS 2.14.0). Cyclone DDS 0.10.4 is Tier 1 but needs extra packages. Gazebo for Jazzy is **Harmonic** ([REP 2000](https://github.com/ros-infrastructure/rep/blob/master/rep-2000.rst); [middleware vendors](https://github.com/ros2/ros2_documentation/blob/jazzy/source/Concepts/Intermediate/About-Different-Middleware-Vendors.rst)).
- **The service recipes do not choose an RMW.** None of them installs an explicit `ros-jazzy-rmw-*` package or sets `RMW_IMPLEMENTATION`. Their package list (`grep ros-jazzy-` across `service-repository/*/Dockerfile.jazzy-debs`) contains none. The images therefore get whatever default the Jazzy dependencies pull in. Each image records `dpkg-query` output in `/usr/share/sdi/installed-packages.txt`, which can confirm the RMW without running the image.
- **Domain ID.** Nodes on the same `ROS_DOMAIN_ID` discover each other; the default is 0. On Linux, IDs 0–101 and 215–232 avoid ephemeral ports. Each participant uses 2 ports, so more than about 120 processes per host per domain can spill into the next domain's ports ([About Domain ID](https://github.com/ros2/ros2_documentation/blob/jazzy/source/Concepts/Intermediate/About-Domain-ID.rst)).
- **Discovery range.** `ROS_AUTOMATIC_DISCOVERY_RANGE` accepts `SUBNET` (the default: "discover any node reachable via multicast"), `LOCALHOST`, `OFF`, and `SYSTEM_DEFAULT`. `ROS_STATIC_PEERS` adds unicast peers ([Improved Dynamic Discovery](https://github.com/ros2/ros2_documentation/blob/jazzy/source/Tutorials/Advanced/Improved-Dynamic-Discovery.rst)).
- **Cyclone discovery.** SPDP goes to multicast `239.255.0.1` by default. `Discovery/Peers` adds unicast addresses, and discovery without multicast "takes longer" ([Cyclone discovery config](https://github.com/eclipse-cyclonedds/cyclonedds/blob/master/docs/manual/config/discovery-config.rst)). `rmw_cyclonedds` documents `CYCLONEDDS_URI` peer lists for setups without multicast ([README](https://github.com/ros2/rmw_cyclonedds/blob/jazzy/README.md)). Cyclone shared memory is built on iceoryx and needs its RouDi daemon and extra build steps ([Cyclone shared memory](https://github.com/eclipse-cyclonedds/cyclonedds/blob/master/docs/manual/shared_memory/shared_memory.rst)).
- **Fast DDS Discovery Server.** It is a client-server alternative that "does not require multicasting capabilities", configured through `ROS_DISCOVERY_SERVER` ([Discovery Server tutorial](https://github.com/ros2/ros2_documentation/blob/jazzy/source/Tutorials/Advanced/Discovery-Server/Discovery-Server.rst)).
- **Fast DDS shared memory in Docker.** Fast DDS enables shared memory and data-sharing by default. It decides "same host" "through a hashing of the network interfaces". As a result, "two Docker container which are not sharing the same network stack will be detected as two different hosts", and Fast DDS uses UDP. Shared memory across containers needs a shared network stack **and** shared IPC. With a shared network stack but separate IPC, the containers are detected as the same host but "will not be able to communicate" ([Fast DDS SHM in Docker](https://github.com/eProsima/Fast-DDS-docs/blob/master/docs/docker/shm_docker.rst)). Discovery itself "is always performed using the UDP/TCP transport" ([Fast DDS shared memory transport](https://fast-dds.docs.eprosima.com/en/latest/fastdds/transport/shared_memory/shared_memory.html)).
- **Compose settings that control sharing.** `network_mode: service:{name}` shares another container's network stack. `ipc: shareable` together with `ipc: service:{name}` shares IPC. `shm_size` sizes `/dev/shm`. `gpus` and `devices` pass through GPUs and `/dev/dri` ([Compose services](https://docs.docker.com/reference/compose-file/services/)).
- **Gazebo headless rendering.** `gz sim -s --headless-rendering` uses EGL without an X server. It works only with OGRE2. "A GPU instance is recommended when sensors that require a render engine are used". Without a GPU, "OGRE will revert to software rendering" ([Gazebo Sim 8 headless rendering](https://gazebosim.org/api/sim/8/headless_rendering.html)).

### Topology options

| Topology | DDS behavior | Costs and risks |
| --- | --- | --- |
| T1. One `internal: true` user-defined bridge per simulation run, one network namespace per container | Each container counts as a separate host, so Fast DDS uses UDP, which avoids the shared-memory mismatch failure. Discovery is multicast SPDP over the bridge (`SUBNET`). | Docker's bridge-driver page does not mention multicast. Whether multicast SPDP crosses a Docker bridge on the target host is **unverified** and needs an empirical check. Fallbacks that avoid multicast are `ROS_STATIC_PEERS`, Cyclone `Peers`, or the Fast DDS Discovery Server, at the cost of per-run configuration. Sensor-heavy topics (camera, lidar) travel over UDP copies. Per-run networks also isolate concurrent or leftover runs without needing distinct domain IDs. |
| T2. Shared network stack and shared IPC with one anchor container (`network_mode: service:sim`, `ipc: service:sim`, anchor `ipc: shareable`) | All participants count as one host, and shared memory and data-sharing work. | All containers share one port space, so the per-host limit of about 120 participants applies. Port collisions between services that bind fixed ports are possible. Losing the anchor container takes down every other container. The default `/dev/shm` size may be too small for image topics, which `shm_size` addresses. |
| T3. Host networking (`--network=host`, plus `--ipc=host` for shared memory) | Shared memory works. Discovery reaches everything on the host LAN. | Breaks stack isolation. The simulation would see, and be seen by, any ROS graph on the host or LAN unless the domain ID or discovery range is also controlled. Under option A it shares the host network; under option B the network is the DinD container's own, which is less clear. The Fast DDS docs warn that `--network=host` without `--ipc=host` fails silently. |
| T4. Shared network stack with **separate** IPC | Fast DDS detects one host, tries shared memory, and fails | Documented anti-pattern. It needs `FASTDDS_BUILTIN_TRANSPORTS=UDPv4` or an XML profile that disables shared memory. |

### Limits specific to this stack and its service images

- **Single cv executor.** The README sets `cv` to 1 executor, so one Jenkins simulation runs at a time per stack. Developer hosts and leftover containers after a timeout can still collide on domain 0 when they share a network.
- **The current assets use Gazebo Classic.** `CV/gazebo/office.launch.py` uses `gazebo_ros` and `gzserver`/`gzclient`, which is Gazebo Classic, and `office.world` is SDF 1.6. Gazebo Classic reached end of life in January 2025, and ROS 2 Jazzy targets Harmonic with "no official Gazebo Classic support" ([OSRF Discourse: Gazebo Classic End-Of-Life & ROS 2 Jazzy](https://discourse.openrobotics.org/t/gazebo-classic-end-of-life-ros-2-jazzy/36239)). Using these assets with Jazzy service images needs a port to Harmonic (`gz sim`, `ros_gz_bridge`). `AGENTS.md` also states the assets are "not wired into the pipeline integration scaffold".
- **Recipe defaults are hardware-oriented.** The `nav2-localization` and `nav2-navigation` default commands pass `use_sim_time:=false`. `turtlebot3-bringup` launches the hardware node on `/dev/ttyACM0` and the LDS drivers (`service-repository/turtlebot3-bringup/robot.launch.py:43,113,124`). A simulation therefore needs command overrides (`use_sim_time:=true`, a `/clock` bridge) and must decide which placements Gazebo replaces. Options include not running bringup, or running only the state publisher.
- **Read-only root filesystems.** If simulation containers copy the agents' `read_only`/`cap_drop` policy, ROS writes logs under `ROS_HOME`/`ROS_LOG_DIR` and those paths would need tmpfs. Whether `read_only: true` keeps a writable `/dev/shm` was not verified here.
- **Architecture.** Images are multi-arch (amd64 and arm64, `SDI.md` `architectures`). The supported host is Ubuntu x86_64, so pulls select amd64, and emulated arm64 is not needed for CV.

## 5. Whether `dispatch-local` can run the same path

Today it cannot. `_local_dispatch.py:57-62` fixes the descriptors to `image-build-fixture-v1.yaml`, `cv-fixture-v1.yaml`, and `cd-fixture-v1.yaml`. `integration/README.md` states that the image-build adapter "runs only in Jenkins … because the builder exists only inside the stack; `dispatch-local` keeps the Fixture". A successful composition run locally ends with image build skipped and CV and CD blocked.

The runtime also refuses to chain an implemented stage after a Fixture: "implemented adapter cannot consume unevaluated Fixture output" (`_stage_runtime.py:893-898`). A real local CV therefore needs a real local `image_build_result`.

Facts that would help a local run:

- **The adapter boundary allows host runs.** `enforce_domain_execution_boundary` returns early when `/etc/sdi/jenkins-agent-role` does not exist (`_jenkins_agent_boundary.py`), so Domain adapters can run on a developer host.
- **Adapters are plain host processes.** The runtime starts adapters with `subprocess.Popen`, environment `PATH` and `LC_ALL` only, not in a container (`_stage_runtime.py:1486-1493, 1630-1646`). The descriptor's `image` field names the agent runtime image, not a container the runtime starts.

Options:

| Option | What it is | Costs |
| --- | --- | --- |
| L1. Keep CV a Fixture locally | Prove the simulation only through Jenkins or `bin/stack exercise-live` | No local parity. Developers iterate on the simulation through the stack. |
| L2. Local real path against the developer's Docker | `dispatch-local` selects implemented image-build and CV descriptors. The image-build path pushes to a local registry. CV pulls from it. | The registry and engine addresses differ between the stack (`registry:5000`, embedded DNS) and the host (for example `127.0.0.1:<port>`). The image-build adapter hard-codes its addresses, and adapters receive no `DOCKER_HOST`. A difference between local and Jenkins would therefore need to be part of the contract (descriptor or Stage-profile data), not the environment. The image-build result's `registry` field would record a different value. The adapter would control the developer's own daemon, which is acceptable on a workstation but gives different isolation evidence. |
| L3. Local run that starts the stack's sidecars | `dispatch-local` (or a wrapper) starts the same `buildkitd`, `registry`, and engine sidecar in an ephemeral Compose project and runs the adapters in a container on those networks | Highest parity, and the addresses stay constant. It reintroduces container orchestration into a command that today runs host processes only, needs a Docker host, and roughly matches what `bin/smoke-check` already does with isolated Compose projects. |

## 6. Unknowns to settle by experiment

1. Whether Fast DDS multicast SPDP between containers on a Docker `internal: true` user-defined bridge works on the supported Docker Engine 27+ host and on Docker Desktop/WSL2. No primary Docker document states it.
2. Which RMW packages the built service images actually contain (read `/usr/share/sdi/installed-packages.txt` from a pushed image).
3. Whether `read_only: true` containers keep a writable `/dev/shm`, and which ROS paths need tmpfs.
4. Whether the target host has a GPU or `/dev/dri`. Without one, Gazebo software rendering may not finish camera and lidar sensor scenarios within the 2700 s CV limit.
5. Disk use and pull time for one scenario's set of Jazzy images, and whether an engine cache volume must persist across `stop`/`start` like `buildkit-state`.
6. Whether a second registry process in read-only mode can safely share `pipeline-registry` while the primary one writes (R2).
7. Container cleanup after a Jenkins timeout kills the CV adapter. Nothing in the stack reaps sibling or nested containers today. Option B's nested daemon bounds the cleanup to one container; option A does not.
8. Whether the trust boundary accepts a second privileged container (option B or E) alongside `buildkitd`, or root-equivalent host-socket access (option A).
